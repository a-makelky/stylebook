## Why the sessions run as Workflow instances

A Queue consumer only raises concurrency after a batch finishes, so one burst of 25 messages can be drained by the first consumer before another starts:

https://developers.cloudflare.com/queues/configuration/consumer-concurrency/

Workflow instances can be created at 100 per second per workflow, and Workers Paid runs up to 50,000 at once. Each step is its own invocation, so one write does not share memory with the others:

https://developers.cloudflare.com/workflows/reference/limits/

The demo route creates one Workflow instance per session (`stylebook-suggestion`). It does not write arrival rows. A different Workflow (`stylebook-arrival`) is started by the namespace-wide push trigger:

https://developers.cloudflare.com/artifacts/guides/build-and-deploy-on-push/

There is no hosted model. The changes are scripted edits to the interview-to-draft skill.

## The four live questions

### Does the namespace-wide trigger fire for copies created after deploy?

Yes. The trigger was deployed at 18:08:03 UTC, before either call. Every suggestion copy in both calls was created during the call, and each of those pushes has one arrival row with `kind` `suggestion`, the copy's name, and the new edition id. A push to `library` is `kind` `library`, not a suggestion.

### Does pushing `refs/notes/*` fire a push event?

Yes. Each call pushed `refs/notes/stylebook` on one suggestion copy, pointing at that copy's new edition, and did not move `main`. Both produced one row with `kind` `notes` and that ref. On the 25-session call the row is repo `sug-agent-7b1952b0-001`, edition `76beb3891bb786bb57f6766ac222c09c4e84782d`. The notes event had no timestamp the parser could read (`detail` starts with `time-missing`), so `arrivedAt` is the time the Workflow recorded the row. The branch pushes did include a timestamp.

### Can a copy be made while a push to the library is in flight?

Yes. Before the 25 sessions, the route saved `desk/probe.md` on the library and started a fork of `sug-agent-7b1952b0-inflight` immediately before that send. The push was in flight from `2026-10-02T18:08:32.151Z` to `2026-10-02T18:08:32.477Z`. The fork was in flight from `2026-10-02T18:08:32.151Z` to `2026-10-02T18:08:35.431Z`. Those intervals overlap. The fork returned `created: true`, `source` `artifacts:stylebook-demo/library`, and no error codes. The same kind of probe on the 100-session call also overlapped and created its copy. The 25 sessions then all forked the library tip from after that probe, so they share one parent.

### How long do 25 forks take?

From the first `forkStartedAt` to the last `forkEndedAt` was 3850 ms. Per session, that window was 1699–3302 ms (median 2384). The window is the whole copy step: a lookup that misses, `fork()`, then `get()` after `fork()` returns. The after-fork `get()` was 11–150 ms, so most of the time is `fork()` itself while 25 run together. A single fork in the earlier run's after-fork `get()` was 48–50 ms; this run still never saw `FORK_IN_PROGRESS`.

The 100-session call's fork windows ran from first to last in 4575 ms, with individual windows of 1526–3810 ms.

The request wall clock is longer than the fork span because it also saves the probe edition, waits for the sessions' writes, pushes the notes ref, and waits for arrival rows.

## What the docs do not say, and what was observed

The queue example of `cf.artifacts.repo.pushed` includes `metadata.accountId` and `metadata.eventTimestamp`:

https://developers.cloudflare.com/artifacts/guides/event-subscriptions/

The docs do not say what a Workflow trigger places on `event.payload`. Every row's `detail` lists the same keys: `id`, `type`, `source.namespace`, `source.repoName`, `payload.ref`, `payload.before`, `payload.after`, `payload.commits`, `payload.totalCommitsCount`, `payload.commitsTruncated`. There is no `metadata` key, so the account id was not in the payload this Workflow received. Branch pushes carried a timestamp string at second precision (`arrivedAt` ends in `.000Z`), which matches a commit timestamp. The notes-ref push had the same keys but no timestamp string. The original payload is not stored, only those key names and the fields the parser understood (repo, ref, edition, time).

The public trigger guide and Wrangler's schema disagree, as noted above. Deploy accepted the schema shape, and the trigger fired for repos that did not exist at deploy time.

No request was refused for rate limit. The published limit is 2,000 requests per 10 seconds per namespace:

https://developers.cloudflare.com/artifacts/platform/limits/

One repo per session, and a fresh write token per write, follows:

https://developers.cloudflare.com/artifacts/concepts/best-practices/

The response bodies contain no write token and no remote URL. Compared by searching the saved bodies.
