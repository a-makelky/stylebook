## What the caller sees

People and agents do not get an Artifacts remote or an Artifacts token. They talk to the Worker. The Worker checks the caller's own key, decides whether that actor may use that copy, and forwards Git's three smart-HTTP requests with a short-lived repo token:

- `GET /git/<copy>.git/info/refs?service=…`
- `POST /git/<copy>.git/git-upload-pack`
- `POST /git/<copy>.git/git-receive-pack`

The `Git-Protocol` header is forwarded unchanged.

https://developers.cloudflare.com/artifacts/api/git-protocol/

A note on an agent-saved edition is pushed under `refs/notes/stylebook`.

https://developers.cloudflare.com/artifacts/concepts/best-practices/

The arrival Workflow confirms each gateway row from the push event by repo, ref, and edition, not by time. A push event with no gateway row is flagged.

https://developers.cloudflare.com/artifacts/guides/event-subscriptions/

https://developers.cloudflare.com/artifacts/guides/build-and-deploy-on-push/

## What the docs do not say, and what was observed

A fetch from the request handler to this Worker's own host returned HTTP 404 with body `error code: 1042`. That code means a Worker tried to fetch another Worker on the same zone:

https://developers.cloudflare.com/workers/observability/errors/

The 25 sessions run as Workflow instances, and those fetches to the Git route succeeded on the upload that did not yet set the flag (23 of 25; the other two failed earlier, inside `fork()`, with `INTERNAL_ERROR`). The library save made from the request handler itself did not. `global_fetch_strictly_public` sends that fetch back through the public front door:

https://developers.cloudflare.com/workers/configuration/compatibility-flags/#global-fetch-strictly-public

After that flag, the same library save succeeded and overlapped the copy, and all 25 sessions succeeded. Stock Git from outside the Worker never needed the flag. The `Git-Protocol` header was left as the client sent it. Clone and push both succeeded, so it was not dropped.

`readFile`'s `ref` is a branch, a tag, or a commit id, in the generated `worker-configuration.d.ts`. The notes ref is not one of those. Reading the notes commit id returns the note. The generated types win over a guess that the ref name would resolve.

The trigger shape is unchanged from the previous run: `targets`, `workflow_name`, `filter.namespace`. Wrangler 4.147 deployed it (`event triggers: 1`).

No response body contained `art_v1_`, an Artifacts remote, a Stylebook key, or the account id. Compared by searching the saved bodies.
